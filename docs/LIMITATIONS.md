# 구현 제한점 — B-CUBE Domain Console

> 기준: 2026-10-27, [SPEC.md](SPEC.md) 전체 구현 시점
> 이 문서는 현재 구현이 **하지 못하는 것**, **보장하지 않는 것**, **확인하지 못한 것**을 모은다. 운영 판단과 다음 개선 작업의 근거로 쓴다.

## 1. 서브도메인 탈취 방지(헬스체크)의 한계

| # | 제한점 | 영향 | 완화 / 개선 방향 |
|---|---|---|---|
| 1.1 | **IP 계열은 "포트가 열려 있는지"만 본다.** 서버가 소유자의 것인지 확인하지 않는다. | AWS Elastic IP를 반납하면 그 IP가 다른 고객에게 재할당될 수 있다. 새 주인이 443/80을 열어 두면 헬스체크는 정상으로 판정하고, `<name>.b-cube.kr`이 남의 서버를 가리키게 된다. **IP 레코드에 대한 탈취 방지는 사실상 없다.** | 소유자가 서버에 토큰 파일(`/.well-known/bcube-verify`)을 두게 하고 HTTP로 확인하는 방식 검토 |
| 1.2 | CNAME 계열은 "응답이 오면 정상"이다. 주인 없음 신호는 Vercel, Netlify, GitHub Pages 3종만 안다. | 다른 호스팅(Render, Fly.io, Heroku, S3 등)에서 앱을 지우면 대상이 응답하는 한 탈취 가능한 상태를 감지하지 못한다. | 벤더 시그니처 테이블(`worker/services/health.ts`의 `VENDOR_SIGNATURES`)에 추가 |
| 1.3 | **벤더 시그니처를 실제 응답으로 확인하지 않았다** (모두 `verified: false`). Netlify의 "Not Found - Request ID" 문구는 추정이다. | 벤더가 응답 형식을 바꾸거나 추정이 틀리면 주인 없음을 놓친다. | 각 벤더에서 도메인을 연결 해제한 테스트 사이트로 실제 응답을 수집해 확정 |
| 1.4 | 일시 중지(suspended) 상태의 재확인은 DNS 레코드가 없으므로 CNAME 대상의 DoH 조회만 한다(`target` 모드). 벤더 주인 없음 신호는 보지 않는다. | `cname.vercel-dns.com`처럼 항상 응답하는 공용 대상은 프로젝트가 없어도 통과해 재활성화된다. 다음 cron 검사에서 다시 실패가 쌓이지만 그 사이(최대 수일) 탈취 가능한 상태가 된다. | Vercel 등은 재활성화 후 즉시 `live` 모드로 한 번 더 검사하고, 실패하면 되돌리기 |
| 1.5 | 검사량은 시간당 10개(하루 240개)다. | active lease가 240개를 넘으면 일부는 하루에 한 번 검사되지 않는다. | `HEALTH_BATCH` 조정 또는 Queue로 분산 |
| 1.6 | 실패는 KST 하루에 한 번만 센다. 소유자의 수동 재확인 실패는 세지 않는다. | 7일 연속 실패해야 일시 중지되므로 최소 6일 넘게 탈취 가능한 상태가 유지될 수 있다(SPEC 의도). | `HEALTH_FAIL_THRESHOLD` 조정 |
| 1.7 | `cloudflare:sockets`는 Cloudflare 소유 IP와 일부 포트에 연결할 수 없다. IPv6 리터럴 연결은 실제 환경에서 확인하지 않았다. | 그런 IP를 쓰는 lease는 항상 실패로 판정될 수 있다. | 운영에서 IPv6 lease로 확인 |
| 1.8 | Worker가 같은 존의 서브도메인(`https://<name>.b-cube.kr/`)에 HTTP 요청한다. 프록시를 켠 레코드는 Cloudflare를 한 번 더 거친다. 실제 운영 환경에서 확인하지 않았다. | 요청이 예상과 다르게 처리되면 오판할 수 있다. | 배포 후 스모크 확인 |

## 2. Cloudflare DNS와 D1의 일관성

| # | 제한점 | 영향 | 완화 |
|---|---|---|---|
| 2.1 | Cloudflare API와 D1은 하나의 트랜잭션으로 묶을 수 없다. 생성·교체 실패 시 롤백은 **최선 노력**이다. | 롤백 실패나 교체 후 기존 레코드 삭제 실패 시 Cloudflare에 레코드가 잠시 남는다. | 작업 기록(`dns_ops`)에 id가 남아 매시 cron이 지운다. 최대 약 70분(10분 대기 + 다음 매시 실행) 남을 수 있다 |
| 2.2 | 반납·회수·만료·일시 중지 중 일부 레코드만 삭제되고 실패하면 lease 상태는 그대로이고, 지운 레코드만 `cf_record_id = NULL`이 된다. | 사용자에게는 502가 보인다. 복구는 **DB 상태(active)가 기준**이라 지운 레코드를 다시 만든다. 사용자가 원한 반납이 자동으로 완료되지는 않는다. | 같은 작업을 다시 하면 된다. 만료·일시 중지는 다음 cron에서 다시 시도 |
| 2.3 | 동시 요청 잠금이 없다. | 같은 사용자가 동시에 여러 개를 만들면 1인당 한도를 넘을 수 있다. 같은 이름 동시 생성은 `uq_leases_name_live` 인덱스가 막고, 늦은 요청의 Cloudflare 레코드는 롤백한다. | 사용자 수 기준으로 위험 낮음. 필요하면 D1 조건부 INSERT로 한도 검사 |
| 2.4 | 동적 충돌 검사는 `<name>.b-cube.kr`과 `*.<name>.b-cube.kr`만 본다(SPEC 범위). `foo.<name>.b-cube.kr` 같은 하위 레코드는 보지 않는다. 또 어떤 레코드든 있으면 충돌로 본다(이 앱이 남긴 잔여 레코드 포함). | 하위 레코드가 있는 이름도 빌려줄 수 있다. 잔여 레코드가 있는 이름은 관리자가 정리할 때까지 빌릴 수 없다. | |
| 2.5 | 무료 플랜의 존 전체 DNS 레코드 개수 한도를 추적하지 않는다. | 한도에 도달하면 생성이 502로 실패한다. | 관리 화면에 레코드 수 표시 검토 |
| 2.6 | 레코드 comment 길이(무료 플랜 100자로 알려짐)는 공식 문서로 확인하지 않았다. 현재 comment는 46자(`bcd:lease=` + UUID). | 영향 없음으로 판단 | |
| 2.7 | 드리프트 점검은 `DNS_DRY_RUN=true`에서 Cloudflare를 조회하지 않는다. | 로컬 dry-run에서는 모든 레코드가 "DB에만 있음"으로 나온다(결과에 안내 문구 저장). | |
| 2.8 | 드리프트의 값 비교는 TXT 따옴표, AAAA 축약, CNAME 대소문자·끝 점만 정규화한다. | Cloudflare가 다른 방식으로 값을 바꿔 돌려주면 "내용 다름"으로 잘못 나온다. 자동 복구가 생겨 영향이 커졌다: 같은 값으로 PATCH를 반복하고, 상세 화면을 열 때마다 복구가 예약되며 `system.dns_repair` 감사 로그가 쌓인다. 실제 API 응답으로 확인하지 않았다. | 운영 첫 점검 결과와 `system.dns_repair` 로그로 확인. 반복되면 `normalizeContent`(`worker/services/drift.ts`)에 규칙 추가 |
| 2.9 | 레코드를 만든 직후, 작업 기록에 id를 쓰기 전에 Worker가 끊기면 그 레코드는 DB에 근거가 없다. | 주간 점검에 "Cloudflare에만 있음"으로 남고 자동으로 지워지지 않는다(SPEC §0-4). 그 이름은 충돌 검사에 걸려 빌릴 수 없다. | 관리자가 대시보드에서 직접 지운다 |
| 2.10 | 자동 복구는 대시보드에서 직접 고친 값도 되돌린다. | 운영진이 급하게 대시보드에서 고친 값이 다음 복구에서 사라진다. | 운영 규칙으로 금지(`DEV.md` 운영 가이드). 기술적으로 막지는 못한다 |
| 2.11 | 상세 화면은 열 때마다 Cloudflare를 1회 조회한다. | 응답이 그만큼 느려진다. 조회 실패 시에는 저장된 값만 보여 준다. 요청 횟수 제한이 없어 반복 새로고침은 Cloudflare API 한도(토큰당 5분 1,200회)를 쓴다(3.1과 같은 문제) | |
| 2.12 | 작업 기록 복구의 잠금은 "3분 동안 다른 실행 거부"다. 한 번의 복구가 3분보다 오래 걸리면 다음 실행과 겹칠 수 있다. | 같은 lease를 두 번 복구해도 결과는 DB 기준으로 같지만, 레코드가 중복 생성될 수 있다. 한 번에 최대 20개라 3분을 넘길 가능성은 낮다. | |

## 3. 인증·세션·보안

| # | 제한점 | 비고 |
|---|---|---|
| 3.1 | 요청 횟수 제한(rate limit)이 없다. | 이름 가용성 조회는 요청마다 Cloudflare API를 2번 부른다(정적 규칙 통과 시). 재확인만 lease당 1분 1회로 제한한다. Workers Rate Limiting 바인딩 검토 |
| 3.2 | 세션은 고정 7일이며 갱신(sliding)하지 않는다. "모든 기기에서 로그아웃" UI가 없다. | 관리자 차단은 모든 세션을 지운다 |
| 3.3 | 세션은 D1에 저장한다(JWT 미사용, 2026-10-27 검토 후 기각). 요청마다 D1 조회 1회. | 즉시 무효화(로그아웃·차단)를 위해서다 |
| 3.4 | `/auth/debug` 클레임은 isolate 메모리에만 있다. | dev 서버를 재시작하면 사라진다. 개발 전용 |
| 3.5 | CSP는 Carbon 때문에 `style-src 'unsafe-inline'`을 허용한다. | SPEC 값 그대로 |
| 3.6 | 실제 Google 계정 로그인과 `hd` 클레임 존재 여부는 아직 확인하지 않았다. | 체크리스트 7번 (사용자) |
| 3.7 | 소유자 화면의 변경 이력은 최근 100건만 보이고, 작업자 이메일·IP는 숨긴다(역할만 표시). | 관리자 감사 로그에는 모두 남는다 |
| 3.8 | 폰트(IBM Plex Sans KR, D2Coding)를 외부 CDN(jsDelivr)에서 불러온다. D2Coding은 subset이라 KS X 1001 밖 한글(예: 똠, 햏)은 다른 글꼴로 표시된다. 방문자 IP와 Referer가 jsDelivr에 전달된다. | jsDelivr 장애나 차단 시 시스템 글꼴로 대체될 뿐 기능은 동작한다. SRI로 변조된 CSS는 막는다. CDN 속도 비교는 한 회선(Cloudflare ICN)에서만 측정했다 |

## 4. 데이터 보존

- `audit_logs`, `reconcile_runs`, 종료된 lease와 그 `records`(이력)는 삭제하지 않는다. 오래 운영하면 계속 쌓인다.
- 만료 처리 cron은 한 번에 최대 50개를 처리한다. 나머지는 다음 날 처리된다.
- 만료된 `sessions` 행만 매일 정리한다.

## 5. 확인하지 못한 것

| 항목 | 상태 |
|---|---|
| 브라우저 화면 확인 (M5 사용자 화면, M6 관리 화면, 375px 모바일 폭) | **미확인.** 타입 검사, Sass 컴파일, dev 서버의 모듈 변환(200)과 API 스모크만 확인했다. 페르소나별 화면 확인은 사용자 확인 필요 |
| 접근성 감사 (키보드, 스크린 리더, 대비) | 미실시. Carbon 컴포넌트 기본 동작에 의존 |
| 운영 배포, 원격 마이그레이션, 시크릿 입력 | 미실행 (SPEC §0-2: 사용자 확인 필요). `wrangler.jsonc`의 `database_id`는 자리표시자 |
| 실제 Cloudflare API로 생성·교체·삭제 | 미확인. 테스트는 가짜 Cloudflare API로 요청 형식과 순서만 검증 |
| 실제 Google OAuth 왕복 | 미확인. 테스트는 가짜 token endpoint와 JWKS로 검증 |

## 6. 시드 데이터

- `member1`(일반 회원 페르소나)은 SPEC §4.3대로 active 2개 + suspended 1개를 가져 **이미 한도(3개)에 도달**해 있다. SPEC §13 M5의 "`user`: 생성 4단계 흐름" 확인은 `newbie` 페르소나로 해야 한다.

## 7. SPEC 범위 밖 (§14)

이메일·메신저 알림(만료 임박은 화면 배너만), 2단계 이상 서브도메인·와일드카드, MX/NS 위임, lease 양도, 결제.
